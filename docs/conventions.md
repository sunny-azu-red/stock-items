# Conventions and rules

These rules keep the app simple, safe and consistent. They apply to people and coding agents alike ([AGENTS.md](../AGENTS.md) is the summary).

## Secrets and data safety

- `.env` holds real credentials and is git-ignored. Never commit it, paste it into issues, or print it in logs. `.env.example` contains placeholders only.
- Tests and experiments never use the `public` schema. Use `internal/testdb` or `DB_SCHEMA=e2e_*` / `test_*`. `db.DropSchema` refuses other names on purpose.
- Deletes don't ask (items, vehicles, kits, services, stock changes, photos, shopping-list entries, archiving): they go to the trash and offer Undo. Only deleting permanently from the *Trash* (Delete permanently, Empty trash) asks first.

## Database

- Migrations are append-only: `internal/db/migrations/000NN_short_description.sql` with the next number, in goose format with `Up` and `Down` sections. `00001_init.sql` is the whole schema as of the squash, and later ones follow it (00002, 00003, …); `TestMigrationFiles` checks the numbering.
- Column order: `id` first, then `version` where the table has one, then the table's own columns (related ones together, notes last), then `created_at`, `updated_at`, `archived_at` and `deleted_at`, in that order, whichever it has. A new table is written in that order. Postgres can't move a column and `ADD COLUMN` puts it last, after the timestamps, so a migration that adds a column calls `SELECT reorder_columns('table', ARRAY[…])` with all of the table's columns in their new order, right after the `ADD COLUMN` (and the Down puts the old order back the same way before dropping it). `reorder_columns` (in `00001_init.sql`; it keeps the rows in an ordinary table while it works, never a temporary one) rebuilds the table inside the migration's transaction: the rows with their ids, each identity sequence at exactly its old value (deleted ids live on in the trash), defaults, NOT NULL and the other constraints and indexes under their names, and other tables' foreign keys to it. It refuses, changing nothing, a list that isn't exactly the table's columns, and a table with something the rebuild would lose: triggers, rules or views, row security, inheritance, grants, comments, storage options, publications, generated columns, column collations, or a sequence that isn't an identity column's own. Trash snapshots don't care, as their keys have no order and restore by name. `TestColumnOrder` checks every table; `TestReorderColumnsKeepsEverything` shows a rebuild keeps everything but the order.
- No temporary tables, in migrations or the store. Postgres keeps a `pg_temp_N`/`pg_toast_temp_N` schema pair for every connection slot that ever made one (the tests use many). Keep scratch rows in an ordinary table that the same transaction makes and drops, as `reorder_columns` does; `TestReorderColumns` fails if a rebuild gives the session a temporary schema.
- Code follows the column order. A Go struct for a table lists its columns in table order, with a joined field right after the foreign key it comes through (`ItemID, ItemName, ItemUnit`), and derived fields and child slices (`SKUs`, `Lines`, `Parts`, counts) after the table's own columns, before the timestamps. SELECT lists and their `Scan`, INSERT column lists and UPDATE `SET` lists (the `version = version + 1` bump first) follow the same order. Display lookups of an item read `brand, name`, the order of `displayName(brand, name)`.
- Use constraints for invariants that must never break: non-negative quantity, valid enums, foreign keys, a service's parts pointing at their service (a CHECK and `ON DELETE RESTRICT`). A migration that adds one first looks for rows (and trash snapshots) that break it and stops with their ids, changing nothing, rather than fix data silently.
- Every delete a user can trigger takes a trash snapshot of the rows it removes, in its transaction (`snapshot`/`putTrash` in `store/trash.go`), and returns the trash id for the Undo button; restoring goes through `RestoreTrash`.
- Never hard-delete a row that other records depend on through a cascade. Refuse it and offer an archive instead, as `DeleteItem` does, so history, services and spending don't change behind the user's back.
- Write all SQL in `internal/store`. Use positional parameters (`$1`), never string-concatenated values. Dynamic filters go through the `sqlArgs` helper.
- Writes that touch more than one row run in `Store.inTx`.
- Every change to an item's quantity goes through `applyMovement`, so the ledger stays complete. The exceptions change a recorded entry together with its effect:
  - `DeleteService` and `UpdateService` return a service's parts through `returnServiceParts`; an update then takes the new ones through `applyMovement`.
  - `UpdateMovement`/`DeleteMovement` revise one movement through `reviseMovement`, which moves the stock by the difference under the item's row lock and refuses to go below zero.
  - `RestoreTrash` puts rows back with their effect (`takeMovements`, `adjustStock`), and undoing a Bought takes its purchase back through `reviseMovement`.
- Lock several items in id order inside one transaction, so concurrent requests cannot deadlock. Lock items `FOR NO KEY UPDATE` to change them (only `DeleteItem` takes `FOR UPDATE`), or `FOR SHARE` to only check them (`AddShopping`): inserting a kit line or movement holds a key-share lock on the item, which `FOR UPDATE` would conflict with. The order is: a service row, its vehicle (`lockVehicle`), the kit it uses (`FOR SHARE`, `checkServiceKit`), then items; a kit's save locks its old and new vehicle (id order) before the kit, and the kit's line items `FOR SHARE` (id order, `shareItems`) after it; a shopping entry before its item; an item before its stock changes (`lockMovement` reads the item id without a lock, locks the item, then the stock change, and checks the id again), as deleting an item locks it before cascading to them; an item before its photo; a vehicle's tags before the vehicle when deleting it. Trash rows come before all of these, in id order (`RestoreTrash` locks its entry before anything else; `PurgeTrash` and `EmptyTrash` lock all theirs before deleting).
- An insert holds only `KEY SHARE` on the rows its foreign keys name, and an `UPDATE` that leaves keys alone doesn't wait for it. When the insert depends on a check that must stay true until commit (the kit isn't archived, the item's unit is the one the kit line's amount was read in), lock the row `FOR SHARE` before checking. A `SELECT … FOR UPDATE` that finds no row locks nothing, so another transaction can insert it meanwhile: look again after taking the lock that keeps such inserts out (`ArchiveItem`, `LinkShopping`). That lookup uses `NOWAIT`, since the entry then comes after the item, against the order (`MarkBought` locks the entry, then the item): when it is held, `ArchiveItem` rolls back to a savepoint, which releases the item, and starts over with the entry first; `LinkShopping` fails with "try again". Foreign-key errors from a row deleted meanwhile become a `ConflictError`, not a 500.
- Every lock-order fix has a forced-interleaving test in `internal/store/locks_test.go`: a third transaction holds a row so the two calls queue up (checked in `pg_locks`) in the order that went wrong, then lets go. It must fail (40P01, or wrong data) without the fix; run it with `-count=5` (CI runs every test in that file so, with `-race`).
- Dates: a `timestamptz` is an instant, kept in UTC, and the session is pinned to UTC (`db.Open`). A calendar day is decided only in Go, in the app zone (`TZ` if set and valid, else the machine's; `main` sets `time.Local` to it): "today" is `stock.DateOnly(time.Now())` (`appToday` in the store), and the day of an instant is `stock.DateOnly(t.In(loc))`. SQL never makes a day from an instant: no `current_date`, `localtime`, `AT TIME ZONE`, `date_trunc`, `extract`, or `::date`/`CAST(… AS date)` on anything but a `$n` parameter; `now()` and `now() - interval '1 day'` are instants and fine. Date columns have no database default; the store always passes the day. `TestNoZoneDependentSQL` reads every string in the store's Go files and fails on such SQL.
- Records that forms edit have a `version` (items, vehicles, kits, services, stock changes, shopping entries). Write the bump in the UPDATE (`version = version + 1`) with a short comment, on every write that changes what the record's edit form or page shows, and say at a deliberate non-bump why (stock quantity, which `quantity_was` guards, and odometer readings, which the vehicle's edit form doesn't have). Check a version after the row lock the function already takes: `lockedVersion` after a `SELECT … FOR UPDATE` (or `FOR NO KEY UPDATE`), or `versionedUpdate` for a single `UPDATE … AND version = $n`. Don't add a lock for it. `restoreRows` gives restored rows a new version.
- A store function behind a create or edit form runs in `inFormTx` with the form's key (`stock.*Input.FormKey`): the claim in `form_submissions` is the transaction's first statement, before any version check or lock, so it holds only its own new row and can't change the lock order. Don't claim a key anywhere else in the transaction, and don't run a form's work in two transactions.
- Archived things take no new work, and the store enforces it inside the transaction, not just the pages: no stock changes to an archived item (a service's own parts move with it when it is edited, deleted or restored), no new services or kits for an archived vehicle, no newly chosen archived kit. Bringing back a deleted past service or kit of an archived vehicle from the trash is allowed, as it isn't new work. Pages hide what the store refuses: the services page of an archived vehicle has no New kit or Log service, and its kits show no reminder. Kit lines may name archived items.
- Autocomplete suggestions (`Suppliers`, `Makes`, `Models`, `Brands`, `Categories`, `Locations`, `KitNames`) are one source each in `internal/store/spellings.go` (the spellings in use as `v`, `pref` 0, and built-in defaults, `pref` 1), listed with `SELECT DISTINCT ON (lower(v)) v ... ORDER BY lower(v), pref, v COLLATE "C"`. `DISTINCT ON (lower(v))` deduplicates case variations, while `v COLLATE "C"` breaks ties deterministically using ASCII byte order (`'A'-'Z'` before `'a'-'z'`). So the capitalized spelling wins on any server, whatever its `LC_COLLATE`; in `Categories` and `KitNames` a value the user typed wins over the built-in default first (`pref`). The CI container initializes with `POSTGRES_INITDB_ARGS: "--locale=C.UTF-8"` for environment parity.
- Saving such a field takes the list's spelling (`spell`, in the write's transaction): text that differs from a spelling another record uses only in case is saved as the list shows it (`ktm` as `KTM`). The record being saved and the built-in defaults don't count, so the only record with a spelling can change its case, and a field whose text is exactly what the record had stays as it is, so saving a record never rewrites a field it didn't change. A new field with suggestions gets a source in `spellings.go` and a `spell` on every write of it.

## Settings

**Preferences and thresholds live in the `settings` table, never in code or the environment.** A number, list, label or format a user could want different (a threshold, a "soon", a grace, a page size, a built-in list, a unit or a format) is a setting on the Settings page. The environment holds only what a deployment needs: the database, the listen address and `TZ`. To add one:

1. A migration: `ALTER TABLE settings ADD COLUMN … NOT NULL DEFAULT <the value the code had>` with a CHECK of its range, then `SELECT reorder_columns('settings', ARRAY[…])` to put it in its section's place (the columns follow the page).
2. `stock.Settings`: the field (in the same place), its `DefaultSettings()` value and its `Validate()` rule; the code reads it with `stock.Current()`. `store/settings.go`: `SettingsColumns`, the SELECT, the scan and the UPDATE.
3. `web/handlers_settings.go`: its `settingDefs` entry in its section of `settingSections` (units and formats, lists, stock, services, warranty; a new area gets a section, in the nav's order): label (its unit in brackets), its "?" (what it changes and anything it doesn't, sentences with full stops) and how it's typed. Under its box goes only its error.
4. Tests: a rule it drives gets a stock test with another value (`settings_test.go`), and the web test saves it over HTTP. `TestSettingsRow` and `TestSettingsComplete` fail on a column without its field, out of order, or with a default other than `DefaultSettings()`.

What stays a constant, with a comment saying why: safety and memory limits (photo sizes and memory, body sizes), validation limits that match a column's size, machine formats (exports, form values, ISO dates), and the shape of the schedule model (the last quarter, at most half the interval).

## Domain

- Quantities are stored in base units (pieces, ml, g) and converted only at the edges (`stock.ParseAmount`, `stock.FormatQuantity`, `stock.SplitForInput`).
- Amounts keep at most two decimals of the base unit, and pieces are whole (`numeric(12,2)` columns, `stock.CheckQuantity`). Finer input is refused with the reason, never rounded; `ParseAmount` checks pieces before any rounding, so `1.0004` isn't read as 1. Amounts the code computes (sums, differences, conversions) go through `stock.RoundQty`, which only drops float noise. Money keeps its own rounding (`FormatMoney`), and prices per ml or g (0.067) are not amounts.
- Pure rules (validation, grouping, due dates, suggestions, exports, how a new item's starting stock is recorded, plausible dates) live in `internal/stock`, have no I/O and are unit tested.
- Money figures (last price, stock value, spending) read only `bought` movements. Stock the user paid for must be recorded as `bought`, never as `starting` or `adjusted`.
- Inputs are cleaned with `Normalize()` and checked with `Validate()`, which returns `stock.Errors` (field → message). Text is limited to 200 characters (4,000 for notes on items, vehicles, kits and services); an over-long field without its own error slot reports on the form's summary (`limitText`).

## Web

- Every page is server-rendered and every form is a plain HTML form (POST, then a 303 redirect with a flash message). JavaScript is assumed: htmx and `static/app.js` may carry a page's behaviour (pickers that send themselves, tabs, adding form rows), and nothing gets a `<noscript>` fallback. The server still never relies on what the browser did (the photo pipeline takes an original as it is).
- Working on a vehicle (`web/working.go`) is a cookie, like the theme, and never a hidden filter. While it is set (two or more active vehicles), a list page (`/`, `/stock`, `/services`, `/activity`, `/shopping`) whose address asks for anything but that vehicle (with General on Stock and Activity) gets a 303 to its address for the vehicle, keeping the rest: the address always says what the page shows, and the bar and the page never disagree. Titles stay plain meanwhile (the bar names the vehicle), the pages hide their vehicle chips and the links to other vehicles' lists, and Log service and Add kit are for the vehicle without asking: new services and kits are for it only (old links open its form, a stale form's save is refused). What belongs to another vehicle (its page, kits, services, their edit forms), the Vehicles list and Add vehicle are out of view: a GET gets a 303 to the vehicle worked on (`elsewhere`), and links to them are names; a save from a page opened before still goes through. Shopping is the vehicle's part of the list (`stock.ShoppingEntry.For`: tagged with it, used by its kits, General or free text), worked out, never stored. Items, Trash, an item's history and the exports are never narrowed (the exports follow their address only). The nav's Vehicles becomes Vehicle (its kind icon, in its colour) and opens its page (the bar's name is no link), and the dashboard leaves out its Vehicles panel; the bar says the vehicle's warranty instead. With one active vehicle it is off, and the cookie is cleared. Test it over HTTP in `working_test.go`.
- Invalid forms re-render with status **422**, keeping exactly what the user typed, with messages next to the fields.
- Every edit form and every button that acts on a record (delete, archive, restore, Bought, link, remove) carries the record's version in a hidden `version` field. A stale edit form (`store.StaleError`) re-renders with 422, keeping what was typed, with the banner "This … was changed since you opened it (another tab or person). Reload to see the latest, then make your change again." and a Reload link (`staleForm`, the `stale` partial). When the record was deleted, it says so and links to the trash. A stale button changes nothing: it flashes the reason and redirects to the record as it is now, or to the trash (`staleButton`). A form whose record was deleted meanwhile never 404s.
- Test forms and buttons over HTTP in `internal/web` (open the page, read the version from the rendered form, change the record in another request, submit), including Undo and Restore paths.
- Every form that creates or changes something carries a one-time key (`{{template "form-key" .FormKey}}`, a hidden `form_key`; the item page's three stock forms each have their own). A 422 re-render keeps the posted key; a fresh page gets a new one. The handler reads it with `parseFormKey`, calls `savedBefore` before it looks at anything the first save may have changed (the version, a ticked-off entry), and maps the store's `AlreadySavedError` with `savedAlready`: nothing is saved again, and it redirects where the first save did with "This was saved already (the first Save went through), so it wasn't saved again. Changes made in the form since weren't applied; check it here." When that record was deleted since, it says so and goes to the trash. A form without a key is not saved: 422 with "This form was opened before Pitbox was updated, so it was not saved. Check it and save again." and a fresh key, since it can't be told from a repeat of itself, and saving it blindly could take a service's parts twice.
- The submit guard in `app.js` locks a POST form once it is sent (htmx forms and the quick +/- excepted). A form with a key says "Saving…" on the button it was sent with; still on the page after 15 seconds, it unlocks and says "Still saving… try again", which is safe because of the key. Coming back with Back (`pageshow`) unlocks and restores the label. Without JavaScript there's no guard, and the key alone keeps a double click from saving twice.
- Test repeats over HTTP too (`formkeys_test.go`): two posts with one key at once (forced to overlap with a held lock), a repeat after the save, after a failed save, of an edit after its own save (not stale), and after Undo.
- A repeating list in a form (an item's SKUs, a kit's parts, a service's parts) ends with exactly one empty row, on add and edit forms alike and when the form comes back with errors (`withEmptyRow`; posted empty rows are dropped when parsing). The Add button adds more; removing the last row clears it instead.
- Never turn a blank field into a destructive value: a blank quantity on the edit form is an error, not 0.
- A calendar day is a `time.Time` at midnight UTC (`stock.DateOnly`, `parseOptDate` with `time.Parse`, and pgx reading a `date`), so a typed `2026-10-31` is that day in any app zone; don't parse form dates with `time.ParseInLocation`. Times shown on pages (`date`, `ago`) are in the app zone: `Server.now` converts the clock to `time.Local`, and pgx scans `timestamptz` into it.
- Parse dates of things that already happened (purchases, stock changes, services) with `parseEventDate`, which applies `stock.CheckEventDate`. Best-before dates use `parseOptDate`; they can be far in the future.
- Sorting: a page's keys are a `sortSpec` in `web/sort.go` (each with its natural direction: dates and amounts descending, text ascending; the stock page starts quantity and best before ascending), read from `?sort=` and `?dir=`; unknown values fall back to the page's default, and links leave out the default key and natural direction. The store turns a key into ORDER BY through its own switch, never by pasting the value, ending with the id so ties and pages are stable; blanks (no price, date, category, location) go last in both directions, and amounts of different units are grouped by unit first. A sortable table header is the `sort-th` partial (`sortHeads.Col`): a plain link with `aria-sort` on the `<th>`; clicking the sorted column flips it, another column starts in its natural direction, the page's other parameters are kept and paging starts over. Sorting is never a filter (`Active()` ignores it, clear filters keeps it), and exports follow it. A form that sorts (the stock page's Sort by) sends what it showed (`was_sort`/`was_dir`), so a new key starts in its natural direction, and answers with the clean URL (a 303, or `HX-Push-Url` for htmx).
- Templates: pages in `templates/pages`, reusable blocks in `templates/partials`, helpers in `render.go`. Use `withQuery` for URLs built from encoded query strings, or a `template.URL` made in Go with `joinQuery` when the link needs more (`sortHeads.Col` adds an `#anchor`).
- Photos are processed only by the libvips tools in a child process (`web/photo.go`), never decoded in Go: one at a time (an upload is checked against its item before its body is read, and beyond four in flight the next is told to try again), with a 30 s timeout, a 100 MP cap and a decode budget read from the header, `VIPS_BLOCK_UNTRUSTED`, one thread, no cache, `JPEGMEM` and a data limit on the child. The user sees a plain message; what vips said goes to the log. `app.js` shrinks a photo before upload, but the server never relies on it. `TestPhotoMemory` keeps the child's peak RSS under its ceilings.
- No external CDNs or fonts at runtime. Vendor assets under `static/vendor` with their licence files: the Manrope font, htmx. (The Lucide icons are inlined as a sprite in `templates/partials/icons.html`; their licence is in `static/vendor`.)
- Browsers: current stable Chrome, on desktop and Android ([AGENTS.md](../AGENTS.md#browser-support-and-the-web-platform)). What it has is used as it is: no fallbacks, `@supports` guards or polyfills. Look features up with the Modern Web Guidance skill or CLI ([development.md](development.md#the-web-platform-modern-web-guidance)), and check them in Chrome.
- Native first: a popover for a sheet, panel or hint, with `interestfor` to show a hint on hover or focus; a `<dialog>` opened with `commandfor`/`command` for a confirmation; `<details>`, `<meter>`, `<search>`; `:has()` to show what a checkbox turns on; `:user-invalid` for field states; anchor positioning for what hangs from something (a hint, a suggestion list). JavaScript (`app.js`) carries only what these can't: repeating form rows, unit pickers and stock badges, suggestion lists, photo shrinking, the clipboard, toasts, tabs, the Appearance panel without a reload (and its swatches kept to one row), the double-submit guard and keyboard shortcuts.
- `app.css` is one file in cascade layers, in order `reset, tokens, base, shell, components, pages, utilities` (the last holds only the spacing utilities `.mt` and `.mb`, so they beat a component's margins). One nested block per component holds its variants, states and container queries, declarations before nested rules. Colours are tokens made with `light-dark()`; never write a colour, and never an accent colour, by hand. Components respond to their own width with container queries (every `.card` is a container, and `main`); only the phone's shell follows the window, at 820px.
- The layout must work from 360 px phone width up. The e2e suite fails if any page scrolls sideways.
- Whole pixels: every box starts and ends on a whole CSS pixel. The browser snaps text to whole pixels but not icons, borders or backgrounds, so text on a fraction moves against its icon from one row to the next (the sidebar's Dashboard sat 1px above its icon while Activity sat level), and a border on a fraction is drawn blurred across two pixels. So, in `app.css`:
  - Set a line height with `--lh` (a factor, like a unitless `line-height`), never with `line-height`: one rule makes every element's line `--lh` times its own font size, rounded to an even number of pixels. A rule that resets the font with `font: inherit` restores that line height right after it.
  - Lengths are `px`; font sizes are `rem`, so the browser's text size scales them (their lines are rounded). No lengths in inline `style` attributes.
  - Heights that something is centred against are even: icons are `round(1.15em, 2px)` or an even px size, checkboxes 14px or 16px, gaps even (a gap is vertical once a row wraps), borders in pairs. Then centring lands on a whole pixel.
  - Text in a box (a button, chip, badge, nav link, count, table header, heading bar) uses a font size whose capitals can be centred in it, measured for Manrope in Chrome: .63–.73rem, .80–.90rem, .97–1.07rem or 1.14–1.24rem; the sizes between leave a whole pixel more on one side of the capitals whatever the padding ([design.md](design.md#text-centred-in-its-box)).
  - A size from a ratio or from the font is rounded: the item photo is `round(78cqw, 2px)` in a size container. Tables use `border-collapse: separate`: collapsed, a cell owns half a border.
  - The e2e test "every box sits on whole pixels and its text lines up" walks every page and form in every e2e project (a 2K screen, a laptop window and a phone). It lists each box that isn't on whole pixels (icons, images, inline text and `.sr-only` are skipped), and text out of line: an icon against the capitals beside it, or the capitals of things side by side in a centred row, by more than 1px; capitals against the middle of their own box (button, chip, badge, nav link, count, table header, heading bar) by more than .3px; and a chip or badge that isn't 24px tall. Table cells default to `vertical-align: middle` so rows with wrapped names or sub-line meters stay vertically balanced with their icons and quantities.
- Spacing comes from one scale ([design.md](design.md#5-spacing)): `--gap` (12px) between cards, sections, tiles and columns, `--inset` (16px, 14px on a phone) inside a card from its edge to its text, `--page` (20px, 14px on a phone) around the page, the same space under the page as above it, and one height for heading bars. On a wide window lists and tables fill the width; a form page stops at `--form-width` (`page-form`), four fields a row (or two, or one: never three), and a side column at 480px. A new component uses the tokens, never a number of its own, and leaves no margin under its last child (a stray `<p>` margin at the end of a card or page once doubled the space under it). The e2e test "every page's spacing follows the scale" checks every page on desktop and a phone. Inside a form, the gaps are set by what you see (a line of text has about 5px of its own above its capitals and under its letters): 10px from a thing to what belongs to it, 17px to the next ([design.md](design.md#6-layout), Forms, Spacing).
- Keyboard shortcuts are global only (the same key does the same thing on every page) and few: the most common actions, `/` Search stock, `a` Add item, `l` Log service. Each is the first letter of the sidebar button it stands for, so a renamed button changes its key. Each shows on what it does, in the sidebar: `/` on Stock (where a count would be), `a` and `l` on their buttons, with `aria-keyshortcuts`; they don't fire in a field, and leaving a form with unsaved changes asks first.
- Accessibility: real `<label>`s for inputs, buttons for actions, links for navigation, `aria-label` on icon-only buttons. Also:
  - A skip link ("Skip to content") comes first and lands on `<main>`.
  - Landmarks have distinct names: the sidebar's nav is "Main", the phone's tab bar "Tabs". The sidebar itself is a plain `<div>`, not an `<aside>`.
  - Filters that change the list are in a `<search>` (Stock). A filter or view that is a link says which one is shown (`aria-current="page"`: the `filter-chip` partial, Grouped/List).
  - Required fields have `required` (the forms keep `novalidate`: the server checks, and its messages use the app's words). `:user-invalid` marks a required field left empty.
  - A field's error is tied to it. The control carries `{{invalid message id …hints}}`, which writes `aria-invalid` ("false" too) and an `aria-describedby` naming the error and the field's hints. The message is `{{template "field-err" (fieldErr message id)}}` (`id`-err). A radio group's `<fieldset>` points `aria-describedby` at its error instead. A message that belongs to no one field (a list's, a row's) stays `{{template "err" …}}`. The error summary reads "Fix the fields marked below." and nothing more; each message is only at its field. It and the stale banner are a red band across the top of the card (or the panel, under its tabs), a heading bar tall, never a box inside a section. The first field to fix has the focus.
  - A "?" hint is named after its field (`"For"` in the `tip` partial: "More about Keep at least").
  - Headings don't skip levels: a card's heading is an `<h2>`. An empty state under it (`"Sub" true`), a stock section under a page's own "Stock for" heading, and a sub-heading inside a form section are `<h3>`.
  - A table has a `<thead>`. Only the column sorted by has `aria-sort`.
  - A status disc says its state (`role="img"` and `aria-label`), unless the row's badges already do.
  - Toasts are announced through one polite live region (`#toasts`, `role="status"`). An error flash is `role="alert"`.
  - Inputs with a suggestion list have `autocomplete="off"`. Part numbers, plates and VINs turn off autocorrect and spellcheck.
- UI standards and components: see [docs/design.md](design.md) for link affordance tiers (dotted underline exclusively for SKUs, solid offset for data fields, no underline for content rows and chips/badges), colour tokens and the accent (`--accent-h`, `--accent-i`, set per device in Appearance), vehicle chips vs status badges (both 24px height, pill vs 4px rounded rectangle in capitals), vehicle entity headings (kind icon colored with vehicle color) vs reference chips, header delimiters, status discs (28px), capitalization rules (Title Case for catalog entities vs sentence case for system labels), focus rings (fields on any focus, buttons on keyboard focus only), and spacing (`--gap` between cards, `--inset` inside them).
- Form hints come in three kinds, each in one place: a hint about one field goes behind a "?" next to its label (`{{template "tip"}}` inside a `.label-row`, with the input's `aria-describedby` pointing at the tip's ID; a sentence with its full stop). A hint about a whole section stays visible as `<p class="hint">` under the section heading, before its fields (no `mb`: `.form-section` spaces it). Under a box goes only its error, inside its `.field` (a card's note about its one box goes over it, as the vehicle page's Odometer's does); what an item picker's text is goes at the end of its box (`.item-box`). Never put a "?" on a heading. Every form follows the Forms rules in [design.md](design.md#6-layout) (sections and headings, hints, spacing as you see it, Notes last, date labels, four, two or one fields a row with none alone, rows on the fields' columns); the e2e tests "every form follows the Forms rules", "a form's rows keep its columns" and "a form's gaps are 10px or 17px as you see them" check them, and a new form's page goes in their lists.

- Record actions sit in the page header ([design.md](design.md#header-buttons)): Edit first, then Duplicate, the other actions, the main (tinted) one, then Archive (plain style, it can be undone) or Delete (red, the trash icon); Restore (primary) on an archived record. No back button. Every button except the main one, a lone button and one that opens a dialog has `data-more` (1 Archive/Delete, 2 Duplicate, 3 Edit, 4 others) and goes into ⋯ (**More actions**) when they don't fit. What acts on a card or list goes in its foot or results heading, small.
- Nothing that can be undone asks first; only the trash's Delete permanently and Empty trash do, in the `confirm-dialog` partial: a `<dialog>` its button opens itself (`commandfor`, `command="show-modal"`), holding the real form, with Cancel focused first and `closedby="any"`. `TestVocabulary` keeps `command="show-modal"` to `trash.html`.
- Form errors start with a capital: `stock.Errors.Add` does it (`stock.Sentence`), so a Go error (lowercase, as Go's are) can go to a form as it is. Don't start an error with a unit ("kg …" would read "Kg …"): "can't use kg for an item counted in ml". Name units in messages as amounts do (`Unit.Short`: pcs, ml, g), never by their code (`piece`).
- An error says what went wrong and what to do, without "Something went wrong" or "Please".
- Required fields carry a red star beside the label (`{{template "req"}}` in a `.label-row`, `aria-required` on the input), and the form a "* required" note at the start of its buttons (`{{template "req-note"}}`). Optional fields aren't marked; like every field, they show an example as their placeholder ("e.g. 24.90"), never "optional".
- A best-before date shows through `{{template "expiry-badge"}}` and how much is in stock through `{{template "stock-badge" (stockBadge …)}}` (out of stock, short, low or what there is; [design.md](design.md#the-stock-badge)), never written by hand; a purchase is entered through `{{template "bought-fields"}}`.

## Code style

- `gofmt`, `go vet` and golangci-lint ([`.golangci.yml`](../.golangci.yml), which includes staticcheck) must be clean (`scripts/check.sh`). A `//nolint` names the linter and says why.
- Tests sit next to the code they test, one file per feature, in the Go way; shared helpers in `store_test.go` and `web_test.go`.
- Exported identifiers get a short doc comment. Comments explain *why*, not *what*.
- Prefer the standard library. Add a dependency only when it clearly pays for itself.
- Tests are table-driven where it helps. DB tests assert the ledger invariant after changing stock.

## Commits

- Small, focused commits. The subject has a type prefix (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `style:`, `ci:`, `chore:`) and says in plain words what changed ("fix: plain Save service and Delete buttons"); the body says why.
- Run the checks the change needs before committing: [AGENTS.md](../AGENTS.md) says which (CSS and templates: the web tests and e2e; Go: `scripts/check.sh`). CI runs all of them on every push.
